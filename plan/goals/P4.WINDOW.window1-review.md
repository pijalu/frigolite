## 1. 32.10 — STALE TEST (frigolite matches modern SQLite)

**SQL**:
```sql
CREATE VIEW a AS SELECT NULL INTERSECT SELECT NULL ORDER BY s() OVER R;
CREATE TABLE a0 AS SELECT 0;
ALTER TABLE a0 RENAME TO S;
```
**Expected**: `error in view a: 1st ORDER BY term does not match any column in the result set`
**Actual**: `<nil>`

**SQLite source**: The "error in view %s" prefix is produced only by
`renameColumnParseError()` (`src/alter.c:1081`, used at `alter.c:1679/1886/2103`) —
i.e. **ALTER TABLE ... RENAME COLUMN**, not `RENAME TO`. `sqlite3AlterRenameTable()`
(`alter.c:124`) rewrites schema SQL via `sqlite_rename_table()` and never re-validates
unrelated views.

**Verified**: sqlite3 3.51 runs the batch successfully; `SELECT * FROM a` errors
`1st ORDER BY term does not match any column in the result set` (no "error in view a:"
prefix). Frigolite behaves identically (view creation/rename OK; using the view errors
with the same message).

**Recommendation**: treat as stale — either update the transpiled expectation to match
modern SQLite (batch succeeds), or skip the assertion. Not an engine bug. (The TCL
test was written against an older SQLite that re-validated views during RENAME TO.)

## 2. 44.3.2 — ENGINE BUG: correlated-agg collapse over empty outer

**SQL**:
```sql
CREATE TABLE t0(c0);
SELECT (0, 0) IN(SELECT MIN(c0), NTILE(1) OVER()) FROM t0;   -- t0 empty
```
**Expected**: one row `0`
**Actual**: no rows

**SQLite mechanism**: the IN-subquery `SELECT MIN(c0), NTILE(1) OVER()` is FROM-less;
`c0` resolves to the outer t0 (correlated). The correlated aggregate collapses the
outer query to an **aggregate query** (one row, even over empty input). VM shows:
aggregate MIN over cursor 0 → NULL; NTILE over the one collapsed row → 1; outer emits
one `ResultRow` (`0` because `(0,0) IN (NULL,1)` → second element 0≠1 → false).
Contrast: `(0,0) IN(SELECT MIN(c0), c0)` (no window) also collapses to one row (NULL);
the window is incidental. And with the subquery given its own `FROM t0`, the outer
returns 0 rows (no collapse).

**Frigolite root cause**: `execSelectCorrelatedAgg` (`select.go:190`) bails when
`len(allRowMaps) == 0`:
```go
if len(allRowMaps) == 0 || !e.hasSubqueryWithCorrelatedAgg(s.Columns) {
    return nil
}
```
The outer scan of empty t0 → 0 rowMaps → returns nil → falls through to the plain
path → 0 rows.

**Fix direction**: when `hasSubqueryWithCorrelatedAgg(s.Columns)` is true and the
scan is empty, produce **one collapsed row** (synthetic all-NULL rowMap), evaluate the
columns with `e.outerRows` set to that single row (correlated aggregate → aggregate
over empty → MIN NULL / window 1). Reuse `evalAggregatesEmpty` semantics for the
aggregate parts. **Risk**: broad blast radius in the corrsubq path (it was recently
changed by 7413e63ca); isolate with a pure-Go test for both the empty and non-empty
outer cases (44.3.2 / 44.4.2).

## 3. 47.2 — ENGINE BUG: GROUP BY ordinal → window function misuse

**SQL**:
```sql
SELECT 234 FROM t2 WHERE k=1 OR (SELECT k FROM t2 WHERE (SELECT sum(a) OVER() FROM t1 GROUP BY 1));
```
**Expected**: `misuse of window function sum()`
**Actual**: `<nil>`

**SQLite mechanism**: `GROUP BY 1` resolves the ordinal to the first SELECT column,
which is the window function `sum(a) OVER()`. `sqlite3ResolveOrderGroupBy()` converts
the ordinal, then the walker finds the window function in GROUP BY and errors
"misuse of window function sum()". Minimal repro:
```sql
SELECT sum(a) OVER() FROM t1 GROUP BY 1;   -- sqlite3: misuse of window function sum()
```
(frigolite: no error).

**Frigolite root cause**: `validateWindowFunctions` (`window.go:2134`) checks
`s.GroupBy` expressions directly; `1` is a literal, not a window FuncCall. It never
resolves GROUP BY ordinals to the SELECT column.

**Fix direction**: in `validateWindowFunctions`, resolve each GROUP BY term via
`resolveGroupByOrdinals` (already exists, `select_agg_walk.go:398`) and run
`windowFuncInExpr` on the resolved expression. **Low risk** — additive validation.

## 5. 65.3 — ENGINE BUG: IN-lhs collation lost

**SQL**:
```sql
CREATE TABLE t1(c1); INSERT INTO t1 VALUES('abcd');
SELECT count() OVER (), group_concat(c1 COLLATE nocase) IN (SELECT 'aBCd') FROM t1;
```
**Expected**: `1 1`
**Actual**: `1 0`

**SQLite mechanism** (`expr.c sqlite3ExprCollSeq:248`): the collation of a function
expression is the first argument's collation; `group_concat(c1 COLLATE nocase)` has
collation NOCASE; the IN comparison uses the LHS collation → `'abcd' IN (SELECT
'aBCd')` compares case-insensitively → 1. (Confirmed with sqlite3: `1|1`.)

**Frigolite root cause**: `evalInList` (`expression_compare.go:345`) evaluates the
operand with `ev.evalExpr(v.Operand, row)` (line 363) instead of
`ev.evalExprWithCollation(v.Operand, row)`, dropping the NOCASE marker that
`exprCollation` (`collation.go:22`, FuncCall → first arg → COLLATE NOCASE) computes.

**Fix direction**: switch the scalar operand evaluation in `evalInList` to
`evalExprWithCollation`. The aggregate path (`evalFuncCall` → `EvalAggFuncCall`) still
returns the plain 'abcd', then `evalExprWithCollation` wraps it with NOCASE. **Risk**:
`evalInList` is hot; verify no regressions in collate8/IN suites. Also check the
row-value operand path (`evalInListOperand` with `operand []interface{}`) — the
operand elements may need the same wrap.

## 6. 67.1 — ENGINE BUG: compound ORDER BY error precedence

**SQL**:
```sql
SELECT a,c,b FROM t1 INTERSECT SELECT a,b,c FROM t1
ORDER BY (SELECT nth_value(a,2) OVER w1 WINDOW w1 AS ( ORDER BY ((SELECT 1 FROM v1)) ));
```
**Expected**: `no such table: v1`
**Actual**: `1st ORDER BY term does not match any column in the result set`

**SQLite mechanism** (`resolve.c resolveCompoundOrderBy:1616`): the compound ORDER BY
term is a scalar subquery. `resolveAsName` → 0; then `resolveOrderByTermToExprList`
(`resolve.c:1541`) **resolves the term's names**, including the nested subquery's
window w1 ORDER BY `(SELECT 1 FROM v1)` — error "no such table: v1" is raised (in the
nested context, not suppressed) and aborts before the "does not match" message.

**Frigolite root cause**: `validateCompoundOrderBy` (`select_validate.go:963`) checks
`compoundOrderByTermMatches` (line 967) without first resolving/validating the ORDER BY
term's nested subqueries. The term doesn't match → returns "1st ORDER BY term does not
match" immediately.

**Fix direction**: in `validateCompoundOrderBy`, before the match check, walk each ORDER
BY term for nested Subquery nodes and validate them (table resolution etc.) so their
errors surface first. **Risk**: order of validation matters across many compound tests
(`INTERSECT/UNION/EXCEPT` + ORDER BY) — run the union/compound suites.

## 7. 71.0 — ENGINE BUG: missing "2 columns assigned 1 values"

**SQL**:
```sql
SELECT a FROM t0, (SELECT a AS b FROM t0)
WHERE (a,1)=(SELECT 2,2 UNION SELECT sum(b),max(b) OVER(ORDER BY b) ORDER BY 2) AND b=4 ORDER BY b;
```
**Expected**: any error (`.*`)
**Actual**: `<nil>`

**SQLite mechanism**: the RHS compound's second member is FROM-less with a correlated
aggregate (`sum(b)`, `max(b)` referencing outer b). During vector codegen
(`expr.c:5500` TK_SELECT_COLUMN: "if pExpr->iTable!=n → %d columns assigned %d
values"), the RHS compound resolves to 1 value against the 2-element LHS vector →
"2 columns assigned 1 values". Isolated: replacing the second member with constants
(`SELECT 2,2 UNION SELECT 3,3`) succeeds; any correlated aggregate/window member errors.

**Frigolite root cause**: the row-value `=` comparison with a compound subquery RHS does
not detect the arity mismatch in this configuration (the correlated aggregate in the
FROM-less member changes the subquery's effective column count during evaluation).

**Fix direction**: locate frigolite's row-value comparison / vector RHS codegen
(`execexpr` `evalRowValueExpr` / binary `=` with subquery RHS) and add the arity check
"2 columns assigned 1 values" when the RHS compound's effective vector size is 1.
Since the test only requires **any** error, a targeted arity validation on row-value
comparisons with compound subqueries suffices. **Risk**: medium — verify the rowvalue
suite (`rowvalue`, `in` tests) for false positives.

## 8. 73.2 — ENGINE BUG: view UPDATE ignores RETURNING

**SQL**:
```sql
CREATE TABLE t1(a INT); INSERT INTO t1 VALUES(1),(2),(4);
CREATE VIEW t2(b,c) AS SELECT * FROM t1 JOIN t1 A ORDER BY sum(0) OVER(PARTITION BY 0);
CREATE TRIGGER x1 INSTEAD OF UPDATE ON t2 BEGIN SELECT true; END;
UPDATE t2 SET c=99 WHERE b=4 RETURNING *;
```
**Expected**: `4 99` × 3
**Actual**: `[]`

**SQLite mechanism**: an UPDATE on a view with an INSTEAD OF UPDATE trigger still
computes RETURNING rows: the matched view rows projected with the SET-clause NEW
values (`4 99` for the three b=4 rows). (Confirmed sqlite3: `4|99` × 3.)

**Frigolite root cause**: `execUpdateView` (`update_split.go:358-405`) fires the
trigger and returns `&Result{Changes: changed}` — **no RETURNING handling at all**. The
regular table path (`update.go`) evaluates RETURNING via `evalUpdateReturning`.

**Fix direction**: add `s.Returning` evaluation to `execUpdateView`: for each matched
(old,new) pair, evaluate the RETURNING projection against the NEW row (the `p.newRow`
already built). **Risk**: moderate — RETURNING validation (column names), OLD/NEW
resolution for INSTEAD OF, and trigger interplay. Check `insert_returning.go` for an
existing view-INSERT RETURNING model to mirror.

## 9. 73.3 — ENGINE BUG: view-join path skips the window pass

**SQL**:
```sql
SELECT *, nth_value(15,2) OVER() FROM t2, t1 WHERE b=4;   -- t2 is a view
```
**Expected**: nth_value = 15 for all 9 rows
**Actual**: nth_value = NULL for all rows (row_number/count OVER also NULL)

**SQLite mechanism**: the outer SELECT over a view joined with a table computes window
functions over the full joined row set. (Confirmed sqlite3: all 9 rows get 15.)

**Frigolite root cause**: `execSelectViewWithOuter` (`select_exec.go:358-405`) — the
view-in-FROM path — has **no window-function pass**. The real-table path
`execSelectPostScan` runs `execWindowPass` at line 71-74; the view path instead goes
straight to `buildOutputRowsFromMaps` (line 396), evaluating `nth_value(15,2) OVER()`
per-row as a plain function without window context → NULL.

**Fix direction**: in `execSelectViewWithOuter`, after WHERE/aggregates, add
```go
if e.selectHasWindowFuncs(s.Columns) {
    winResult := e.execWindowPass(s, rowMaps, viewColDefs)
    return e.finalizeSelectResult(winResult, s, winResult.rowMaps)
}
```
(mirroring `execSelectPostScan`). **Risk**: low-medium — the view path also handles
ORDER BY/LIMIT via finalize; ensure the window result feeds those correctly.

## 10. 73.4 — ENGINE BUG: window fn in view UPDATE SET

**SQL**:
```sql
UPDATE t2 SET c=nth_value(15,2) OVER() FROM (SELECT * FROM t1) WHERE b=4 RETURNING *;
```
**Expected**: `4 15` × 9
**Actual**: `no such function: nth_value`

**SQLite mechanism**: the SET expression is a window function; SQLite computes it over
the UPDATE's target rows (with FROM) → c=15 for all rows; RETURNING emits `4 15` × 9
(via the INSTEAD OF trigger path).

**Frigolite root cause**: `execUpdateView` → `applyViewSetAssignments`
(`update_split.go:457`) evaluates each SET value with `e.ctx.EvalExpr(a.Value, evalRow)`
— no window-function support → `nth_value` isn't recognized → "no such function".

**Fix direction**: evaluate window functions in UPDATE SET expressions on views by
routing them through the window engine (collect window FuncCalls in the SET clause,
compute over the matched view rows, substitute per row). Also confirm the plain-table
UPDATE ... FROM window path (`update.go`) — the 73.4 statement targets a view, but the
same gap may exist for table UPDATE SET with window functions. **Risk**: medium — the
window pass expects a `SelectStmt`; may need a small adapter to run over the UPDATE's
row set.
