## Root-cause summary (from SQLite source review)

### Task 1 — consumption-rate (1.3/1.5, 5.7–5.11, 4.3, 6.1)

SQLite's `sqlite3Fts3Incrmerge` (fts3_write.c:4925) merges with:

- `nRem = nMerge` (leaf-page quota).
- Writer with `nLeafEst` (SQL_MAX_LEAF_NODE_ESTIMATE = `2*total(1+leaves_end-start_block)`
  over the nSeg oldest source segments) and `iBlock` starting at `iStart`.
- `fts3IncrmergeAppend` (fts3_write.c:4017) appends each term to the leaf buffer;
  flushes to `%_segments` when `block.n>0 && block.n+nSpace>nNodeSize &&
  iBlock<iStart+nLeafEst` (increments `nWork`, `iBlock++`, buffer = overflow term).
- The do-while stops when `nWork>=nRem`.
- **Key**: after a quota stop the in-memory leaf buffer holds only the overflow
  term → the stored last leaf is nearly EMPTY. The next merge's
  `fts3IncrmergeLoad` resumes from that nearly-empty buffer → consumes a full
  page per call. When the pre-allocated range is exhausted (`iBlock >=
  iStart+nLeafEst`) the flush condition is always false → `nWork` stays 0 → the
  merge NEVER stops → drains ALL remaining source terms in one call
  (fts4merge 1.3 merge #3; 5.7–5.11).

The engine's `MergeFTS` (internal/execddl/export.go:940):
- Simulates a buffer with `continuationBuf = actual last-leaf size` of the
  output. But the output is REBUILT via `SegmentRootBlocks(docIDs)` →
  `serializeSegmentBlocks` packs the last leaf FULL → the next merge's
  continuation starts near-full → flushes after 1–3 terms → consumes ~3
  terms/merge instead of a full page. **This is the consumption-rate bug.**
- Also missing the `nLeafEst` bound → cannot reproduce the "drain all" regime.

**Fix (faithful)**: rewrite MergeFTS's output path so the output is built from
the merged TERM STREAM with SQLite's flush semantics:
1. Simulate the merge over the sorted refs with an explicit `nLeafEst` and
   `iBlock` counter; the flush condition = `buffer>0 && buffer+size>nodeSize &&
   flushed < nLeafEst`.
2. Output = the merged terms serialized with the SAME packing: full leaves for
   each simulated flush + last leaf = ending buffer (nearly empty after a quota
   stop; all remaining terms when draining).
3. Continuation: load the existing output's last leaf (now nearly empty) as the
   continuation buffer; keep existing leaves, append new ones; rebuild the
   interior root over all leaves (block IDs are allocated on demand after
   max(blockid) — the tests do not pin exact block IDs; fts4check/fts4intck1
   check validity only).
4. `nLeafEst` for a continuation = `(endBlock-startBlock+1)/16` per
   fts3IncrmergeLoad; for a fresh merge = `2*Σ(1+leaves_end-start_block)`.
   Draining happens when `flushed >= nLeafEst`.

This also removes the latent term-duplication (rebuilding output from doc IDs
re-includes unmerged source terms) and makes each merge O(terms consumed)
instead of O(output) — prerequisite for task 3.

**Verify each**: 1.3 (drain L1 by merge #3 → "2 0 1 2 3"), 1.5 ("3 0"),
4.3 ("2 then 1/merge" loop), 5.7/5.8/5.10/5.11 (hint bytes X'010F'/X'010E',
level/idx lists), 6.1 (merge=1,2 no corruption).
