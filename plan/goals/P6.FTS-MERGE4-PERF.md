# P6.FTS-MERGE4-PERF — fts4merge4 oracle performance measurement

> **Status**: MEASURED (2026-08-24, goal `jade.puma`).
> **Method**: identical workload replayed under `/usr/bin/sqlite3` (3.51.0)
> and frigolite; timings on Apple M-series, single connection.
> **Workload source**: `../sqlite/test/fts4merge4.test` section 2.2 —
> `doc` = the 1000 three-char tokens `aaa..jjj` repeated 10× (~40 KB,
> 10k tokens); 100 transactions × 5 INSERTs of `doc`; configs
> automerge ∈ {1,2,4,8} × {same-connection, reopen-every-10-txns}.
> Generator equivalent recorded in this file §5 (script form).

## 3. Slowdown factor

- automerge=2 @100 txns: 1.31 s vs 0.42 s ⇒ **~3–4×** (acceptable range).
- automerge=1: per-txn cost GROWS LINEARLY with completed txns
  (25.9 → 59.1 → 98.7 ms) ⇒ total cost is **quadratic** O(n²).
  Extrapolated ≥ 16 s at 100 txns for ONE pass; the e2e suite runs 8 passes
  (4 configs × open/reopen) plus `DELETE FROM t2` resets — measured e2e:
  **>15 min at commit 8af1ece11 (timeout)**, **1048 s at HEAD** (completes,
  8 correctness mismatches owned by P6.FTS-G).
- Effective slowdown vs oracle at the tail: **50–500× and unbounded**
  (quadratic vs linear).

## 4. Hotspot localization

1. **Per-txn cost scales with live segment count** (automerge small ⇒ many
   level-0 segments accumulate): every flush's automerge attempt re-runs
   FIND_MERGE_LEVEL and primes a fresh k-way reader heap over ALL oldest
   segments (`internal/execddl/export_fts_merge.go` MergeFTS loop +
   `fts.NewSegmentStreamReader` priming), and chomp truncation rescans
   sources. SQLite bounds this with incremental SegReaderStep consumption
   charged against nRem — the engine instead pays full segment scans whose
   size grows every txn.
2. **Per-statement pager snapshotting**: stack captured during the e2e hang
   shows `execSnapshotDML → snapshotAllPagers → (*Pager).Snapshot`
   (`internal/exec/engine_tail.go:307`) copying ALL cached pages per DML
   statement (`internal/pager/pager.go:91 Snapshot`) invoked via
   `writeFTSStatRow` during FTS inserts
   (`internal/execddl/export_fts_flush.go:824`). Snapshot cost is O(cached
   pages), which also grows with the working set ⇒ second quadratic term.

## 5. Workload script (verbatim generator)

```
tokens = [c1 c2 c3 for c1,c2,c3 in "a".."j"³]   # 1000 tokens
doc    = " ".join(tokens * 10)                   # ~40 KB, 10k tokens
CREATE VIRTUAL TABLE t2 USING fts4;
INSERT INTO t2(t2) VALUES('automerge=<N>');
repeat 100: BEGIN; 5 × INSERT INTO t2 VALUES('<doc>'); COMMIT;
SELECT level||':'||count(*) FROM t2_segdir GROUP BY level;
```

Oracle run command: `sqlite3 /tmp/o2.db < /tmp/m4_am<N>.sql`.

## 6. Conclusions / next actions

- fts4merge4's e2e slowness is a PRE-EXISTING performance divergence, NOT a
  regression of the P6.FTS-WPORT varint/continuation work (baseline commit
  8af1ece11 timed out at 1500 s; HEAD completes in 1048 s — an improvement).
- Correctness mismatches (8 assertions, level distribution) remain owned by
  P6.FTS-G per PORTPLAN.
- Performance fix candidates (future goal): quota-charged incremental
  readers for automerge attempts (mirror SegReaderStep/nWork accounting),
  and eliminating whole-pager Snapshot per DML statement (statement
  rollback should snapshot dirty pages only, or use journaling).
