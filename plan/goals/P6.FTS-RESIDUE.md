## SEG3 allocator narrowing (2026-09-09)

The missing block: level=32 idx=16, start_block=1036 (a cascade-depth
segment from an early allocation round). Prime suspect: the block-id
allocator. ftsNextBlockID caches next-block-id on the FTS3Table
(NextBlockID/SetNextBlockID, seeded from max(blockid)+1). The chomp
DELETES high blocks (a consumed segment's [start, leaves_end] range and
a truncated segment's leading dead run) — if the allocator cache is
subsequently invalidated and recomputed from the lowered max, or a NEW
FTS3Table object (freshFTSFromSegmentsForIndex builds one per cascade
step) re-derives its cache after deletions, ids get REUSED under
segments whose own [start, leaves_end] ranges lie above the deleted
range. A reused range that covers level-32/idx-16's block 1036 makes
readFTSBlock fail [SEG3].

Next actions: (1) audit every SetNextBlockID/invalidation site against
the chomp's deletion order; (2) make the block-id derivation strictly
monotonic (never below the previous cache value, C's p->iNextBlock
semantics); (3) acceptance = fts4opt's merge=5,2 runs without [SEG3]
and the 1.x level-count assertion pins 5 segments per cascade level.
The instrumentation: FRIGOLITE_FTS_DEBUG=1 writes the failing
level/idx/start to a temp file from validateFTSSegmentsCheck's SEG3
site (re-add the temporary block there).

## ROOT CAUSE identified (2026-09-09) — SeekToRowID mis-routes on merge-built %_segments trees

Decisive probe: at the [SEG3] failure, `SELECT blockid FROM t2_segments
WHERE blockid BETWEEN 1030 AND 1042` returns ALL of 1030-1042 (the SQL
scan traverses fine), but `cursor.SeekToRowID(1036)` returns
not-found. The block exists; the SEEK is broken.

Why: %_segments' btree was built by the merge writer's layered
hierarchy (IncrLeafWriter.BeginHierarchy/SeedHierarchySeps), which
produces interior pages — including zero-cell interiors — whose
separators do not satisfy seekInInteriorTable's binary-search
invariants (keys <= separator route left; the rest rightmost). The
scan path (ReadCellData + advanceCursor) handles the same tree fine —
which is why reads via SQL work while readFTSBlock's
SeekToRowID-based lookup fails. merge=5,2's loop runs merge=5,2
repeatedly (1.6 loops until TotalChanges delta < 2); each iteration's
pre-merge ValidateFTSSegments walks segdir and readFTSBlock's
SeekToRowID mis-routes on the merge-built tree -> [SEG3] errors (1796
of them) until the loop ends.

Fix options (next session): (a) fix seekInInteriorTable to handle the
hierarchy-built interior structure (0-cell interiors route to
rightmost; separator ordering must match the writer's layer
construction); or (b) make the hierarchy writer emit separators
consistent with the seek invariant. Verify with the fts4opt merge=5,2
loop (no [SEG3] errors) and the fts4merge family staying green.
