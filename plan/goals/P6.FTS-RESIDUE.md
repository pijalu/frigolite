## fts4opt root cause narrowed (2026-09-09)

Probe (KJV Genesis load into fts4(words, prefix="1,2,3"), then
'integrity-check'): the failing raise is IntegrityCheckIndex/
compareExpectedBand — band=0, expected=20 terms (ONE document) vs
2448 actual index terms. The %_content btree has 1533 rows, but the
docs map built by the cursor.ReadCell loop in RunFTSIntegrityCheck
(internal/execddl/export.go:330-345) contains only ~1 document: the
loop breaks on the first cursor error/end at a PAGE BOUNDARY.

Root cause queue: btree Cursor.ReadCell()/advanceCursor stops (returns
err) when the scan crosses into the next leaf page on a multi-page
%_content btree. Fix the traversal (or the loop's error handling to
distinguish a genuine corruption from end-of-scan/page transitions),
then the integrity-check sees all 1533 docs and band 0's expected
term count matches the 2448-term index. Sentinel-based triage
(temporarily tagged raise sites) identified the site; sentinels
reverted. Acceptance: TestZZOptProbe-style probe passes (small probe:
load KJV Genesis into fts4 prefix=1,2,3, run integrity-check, expect
ok) plus the fts4opt package flipping fail->pass.

## fts4opt integrity-check FIXED (2026-09-09) — rowid-alias docid in the content scan

Root cause correction: the page-boundary theory was wrong — the walk
visited every row. The real defect was the rowid-alias convention:
`t2_content.docid` is an INTEGER PRIMARY KEY stored NULL in the record,
so RunFTSIntegrityCheck's `rec.Values[0].(int64)` failed for EVERY row
and `docs[0]` was overwritten 1533 times — the integrity-check compared
ONE re-tokenized document (20 terms) against the full 2448-term index.

Fix: the docid comes from `cell.RowID` (the authoritative rowid-alias
value), exactly like the external-content path already did. The probe
(KJV Genesis -> fts4 prefix=1,2,3 -> integrity-check) now passes with
docs=1533 across all four bands.

Remaining fts4opt failures are MERGE PARITY, a different gap: merge=5,2
produces 9 segments per level where SQLite produces 5 (fts3_write.c
incrMergeChains' segment-count/target-leaf semantics), and later level
aggregation counts differ ([0 1 32 33 ...] vs [0 2 1024 2 ...]). The
merge port needs fts3_write.c's inner-merge loop compared line-by-line
— next batch.

Also landed while narrowing: navigateToNextChild's rightmost branch
uses >= so degenerate zero-cell interior pages (append-split chains)
are traversed instead of ending the walk, and the rightmost navigation
pops the parent (prevents a re-navigation cycle). Sentinel debug
instrumentation reverted.

## SEG3 allocator narrowing (2026-09-09)

The missing block: level=32 idx=16, start_block=1036 (a cascade-depth
segment from an early allocation round). Prime suspect: the block-id
allocator. ftsNextBlockID caches next-block-id on the FTS3Table
(NextBlockID/SetNextBlockID, seeded from max(blockid)+1). The chomp
DELETES high blocks (a consumed segment's [start, leaves_end] range and
a truncated segment's leading dead run) — if the allocator cache is
subsequently invalidated and recomputed from the lowered max, or a NEW
FTS3Table object (freshFTSFromSegmentsForIndex builds one per cascade
step) re-derives its cache after deletions, ids get REUSED under
segments whose own [start, leaves_end] ranges lie above the deleted
range. A reused range that covers level-32/idx-16's block 1036 makes
readFTSBlock fail [SEG3].

Next actions: (1) audit every SetNextBlockID/invalidation site against
the chomp's deletion order; (2) make the block-id derivation strictly
monotonic (never below the previous cache value, C's p->iNextBlock
semantics); (3) acceptance = fts4opt's merge=5,2 runs without [SEG3]
and the 1.x level-count assertion pins 5 segments per cascade level.
The instrumentation: FRIGOLITE_FTS_DEBUG=1 writes the failing
level/idx/start to a temp file from validateFTSSegmentsCheck's SEG3
site (re-add the temporary block there).
