# P6.RTREE — RTREE Virtual Table Module (feature-complete port)

## Objective

Implement the SQLite `rtree` / `rtree_i32` virtual table modules in frigolite,
feature-complete and SQLite-compatible, per the user directive:
*"implement rtree - frigolite must be feature complete"*.
Design mandate (user refinement): **use Go generics / idiomatic features to
optimize rtree and stay SOLID** — faithful algorithm, but written idiomatically
(NO SIMPLIFY applies to the *algorithm/fundamental approach*, not to a
line-by-line C transliteration).

Source of truth: `../sqlite/ext/rtree/rtree.c` (4485 lines) + `rtree.h`,
oracle `/usr/bin/sqlite3` 3.51.0, TCL tests `../sqlite/test/rtree*.test`
(rtree1..rtreeN).

## Context

- `internal/vtab/vtab.go` currently registers `rtree` as
  `&NoopModule{ModuleName: "rtree"}` (line ~110) — non-functional.
- Frigolite virtual-table modules have **no access to the main database**
  (no shadow-table creation, no SQL execution, no function registration).
  The existing precedent is `sqlite_dbpage`, wired via constructor DI:
  `e.vtabs.Register("sqlite_dbpage", vtab.NewDBPageModule(enginePageSources{e: e}))`
  at `internal/exec/engine.go:815`. This is the Open/Closed (OCP) + Dependency
  Inversion (DIP) pattern to reuse.
- The `Module` interface is `Create(args []string) / Connect(args []string)`.
  Breaking it is forbidden; we inject capability through the **constructor**
  (a `*RtreeModule` holds a `vtab.Database` handle), exactly as dbpage does.

## Architecture Decision (SOLID + DIP)

### New interface `vtab.Database` (`internal/vtab/rtree_db.go`)
Defines the capability a vtab module needs, implemented by `*exec.Engine`.
Keeps `internal/vtab` free of any import of `exec`/`sql`/`function` (no cycle;
`exec` already imports `vtab`).

```go
// Database is the engine capability a vtab module needs to manage its shadow
// tables and register SQL functions. Satisfied by *exec.Engine (DIP: vtab
// depends on this interface, not the concrete engine).
type Database interface {
    // ExecSQL runs DDL/DML/SELECT. Returns rows (empty for non-SELECT) or error.
    ExecSQL(sql string, args ...interface{}) ([][]interface{}, error)
    // RegisterScalar registers a scalar SQL function.
    RegisterScalar(name string, minArgs, maxArgs int,
        fn func(args []interface{}) (interface{}, error))
    // RegisterAggregate registers an aggregate SQL function.
    RegisterAggregate(name string, minArgs, maxArgs int, newAgg func() Aggregator)
}

// Aggregator is the vtab-local aggregate contract (avoids importing function pkg).
type Aggregator interface {
    Step(args []interface{})
    Final() interface{}
}
```

`internal/exec/engine.go` adds an adapter satisfying `vtab.Database`
(`ExecSQL` parses+execs via `e.Exec`; `RegisterScalar`/`RegisterAggregate`
delegate to `e.RegisterFunction`/`function.Registry.RegisterAggregate`,
wrapping `vtab.Aggregator`→`function.Aggregator`). Engine registers rtree at
construction:
`e.vtabs.Register("rtree", vtab.NewRtreeModule(e.Database()))` and similarly
`"rtree_i32"`.

## rtree module design (generics + SOLID file split)

Generic over the coordinate scalar type `T` ∈ {`float32`, `int32`}:
- `rtree` → `Rtree[float32]` (RTREE_COORD_REAL32)
- `rtree_i32` → `Rtree[int32]` (RTREE_COORD_INT32)

`RtreeCoord[T]` union replaced by a type parameter; all geometry math
(union/overlap/area/margin/contains) is generic. Serialization
(`readCoord`/`writeCoord`) is specialized per `T` via a small `coordCodec[T]`
interface to keep `NCELL`/cell packing faithful to rtree.c byte layout
(8-byte rowid + nDim2×4-byte coords).

### Files (each single-responsibility, cyclomatic ≤12)
- `internal/vtab/rtree_db.go` — `Database`/`Aggregator` interfaces, `NewRtreeModule(db, coordType)`, registration helper, shadow-name helpers (`rtreeShadowName`).
- `internal/vtab/rtree.go` — `RtreeModule`, `RtreeVTab[T]`, `Create`/`Connect`, `declareSchema` (mirrors `rtreeInit` argv parsing: dim/aux-column validation, `nodesize=N`), shadow-table DDL creation (mirrors `rtreeSqlInit`), `BestIndex` (pass-through full scan + geometry/MATCH constraint capture), `Open`, `Column`, `Rowid`, `UpdateRow` (delete+insert), `Rename`, transaction/savepoint hooks.
- `internal/vtab/rtree_node.go` — node blob codec (`RtreeNode[T]`), cell (de)serialization, node hash cache (`nodeHash`/`nodeAcquire`/`nodeRelease`), `nodeInsertCell`/`nodeDeleteCell`/`nodeOverwriteCell`/`nodeWrite`, root creation.
- `internal/vtab/rtree_query.go` — `rtreeFilter` + priority-queue search (`RtreeSearchPoint`, `rtreeStepToLeaf`, `rtreeEnqueue`), leaf/nonleaf MBR constraint eval (`rtreeLeafConstraint`/`rtreeNonleafConstraint`), `rtreeCallbackConstraint` (MATCH via geometry callback), `findLeafNode`.
- `internal/vtab/rtree_write.go` — `rtreeInsertCell`, `ChooseLeaf`, `SplitNode` (R*-tree split: margin/overlap scoring, `SortByDimension`, `startree`), `AdjustTree`, `fixBoundingBox`, `deleteCell`, `removeNode`, `fixLeafParent`, `rtreeNewRowid`, `rtreeDeleteRowid`.
- `internal/vtab/rtree_func.go` — SQL scalar/aggregate functions registered in `Connect`: `rtreenode(N, blob)`, `rtreedepth(N, name)`, `rtreecheck`, `BuildRtree` (bulk load → `sqlite3_rtreebuild`/`rtreebuild` INSERT-over-SELECT), `rtreegeometry`, and the `r-tree` geometry query callback function used on the right of MATCH.

### Shadow tables (faithful to rtree.c)
- `<name>_rowid(rowid INTEGER PRIMARY KEY, nodeno, a0..aN)` — entry→node + aux cols.
- `<name>_node(nodeno INTEGER PRIMARY KEY, data BLOB)` — one node per blob.
- `<name>_parent(nodeno INTEGER PRIMARY KEY, parentnode)` — node→parent.
- `<name>_shadow(...)` — savepoint/rollback journal (lazy; needed for full
  transactional correctness, included in final slice).
Read/write via the `Database` interface using the 8 parameterized statements
from `rtreeSqlInit`.

### Geometry MATCH
Mirrors `rtreeFilter`: constraints include `col >= / <= / < / > / = val` and
`rowid IN (...)` plus `mbbox MATCH <callback>(...)`. The MATCH callback is a
SQL function (`r-tree`/`rtreegeometry`) registered by the module that receives
the cell MBR and returns 0/1; the cursor evaluates it per leaf cell.

## Risks / Decisions
- **No CGO, pure Go**: faithful byte-level node codec; coordinate float32 must
  round-trip exactly like SQLite's `RTREE_COORD_REAL32` (stored as 4-byte
  float, not double) — critical for MBR equality vs oracle.
- **Shadow tables as real SQL tables**: frigolite must persist them in the main
  schema (not just in-memory) so `ATTACH`/savepoint semantics hold. Engine
  `ExecSQL` routes to the same pager.
- **Generic coord math**: keep `T` constrained to `float32 | int32`; serialize
  via `coordCodec[T]` to avoid reflection in hot paths.

**Shared prerequisite — the `vtab.Database` interface (slice 1 of P6.RTREE):**
rtree, fts5, dbdata and dbstat ALL need a vtab module to (a) create/read/write
shadow or backing tables via SQL and (b) register SQL functions. The
`vtab.Database` DIP interface built in slice 1 is the single shared
capability all four modules depend on. Once it lands, each sibling goal can
be executed independently against the same engine adapter.

This goal (P6.RTREE) delivers the framework + rtree. fts5/dbdata/dbstat have
their own dedicated plan/goal files (plan/goals/P6.FTS5.md, P6.DBDATA.md,
P6.DBSTAT.md) and are queued as sibling goals. The `fts3`/`fts4`/`fts4aux`
Noop wiring is corrected by registering the already-existing
`internal/fts` modules (no new algorithm code required).
