### Batch 11 (sqllimits1 tranche 2) — 2026-09-06 — 21/24 pass, sqllimits1 down to 1 failure

THREE root causes found and fixed (all pure-Go-discriminated, /tmp/sqllimitsdisc):

1. **Rowid-cache corruption on UPDATE (row LOSS — batch 10's nested-INSERT
   bug)**: `writeUpdateCell` invalidated the rowid cache after EVERY row
   write; the following monotone `BumpRowIDCache(writeRowID)` re-seeded the
   entry with just that row's rowid. A trigger body inserting during the
   same UPDATE then re-allocated EXISTING rowids, and the per-row
   re-read-and-write clobbered the inserted rows (sqllimits1-7.4 cascade:
   oracle 7 rows, ours 4; minimal repro: 3-row table + BEFORE-UPDATE INSERT
   trigger lost 2 of 3 inserts and corrupted content). Fix: invalidate only
   when writeRowID != ch.rowID (in-place updates keep the max); for a real
   rowid change bump-then-invalidate (max may have been the removed one).
   Cascade now oracle-EXACT (7 rows, row-for-row).

2. **Schema btree refused freelist reuse at the page cap**:
   `BTree.allocPage` used `AllocatePageSkipFreelist` for ALL schema-btree
   allocations (INCRVACUUM phase9), so at `max_page_count` a CREATE VIEW
   failed SQLITE_FULL with 1690 freelist pages available. SQLite allocates
   schema pages from the freelist in plain (non-autovacuum) databases;
   skipFreelist is now conditional on AutoVacuum (sqllimits1-8.8 ✓).

3. **O(rows x tree) UPDATE hot loops** (made the 7.5 cascade take >236s and
   time out): (a) `updateRowConflictsWithTable` ran a full-table scan per
   updated row — now skipped entirely when the SET clause assigns no
   UNIQUE/PK/index column (no conflict is possible); (b) per-row
   `DeleteCellsWhere` swept the whole tree — new `BTree.DeleteCellByRowID`
   does an O(log n) cursor seek + targeted leaf delete. Cascade 236s -> 24s.
