# Nested join-group duplicate-name repair plan

## Reproduction and source contract
- `go test . -run '^TestP6_NestedJoinSameName$' -count=1` fails both source-faithful cases from `../sqlite/test/selectD.test:77-108`. SQLite CLI confirms outer query should return `111|x1|222|x2|444|x4|555|x5`.
- Added a temporary diagnostic test (removed after run) tracing nested levels. Plain `main.t4 JOIN aux1.t4` returns correct `[444 x4 555 x5]`. One enclosing group returns `[222 x2 555 x5 555 x5]`; next outer group returns `[111 x1 555 x5 555 x5 555 x5]`.
- Evidence localizes defect to the materialized join-group boundary, not initial table scans or qualified ON evaluation. `materializeSubqueryJoin` calls `buildSubqueryRowMaps` (`internal/execquery/select_join.go:318+`); that reuses rowmaps then overwrites `maps[rowIndex][def.Name]` from each displayed result column (`select_join_derived.go:18-30`). Duplicate result names such as both `a`/`b` from main.t4 and aux1.t4 collapse to one unqualified map key. `projectSubqueryRowMaps` retains qualified keys but outer star projection's duplicate column names resolve through the clobbered unqualified value.

## Plan before edits
1. Inspect `execSelectJoins`/star projection data flow and SQLite `select.c` join-group/co-routine semantics. Determine whether output column identities can be preserved positionally without changing duplicate-column resolution elsewhere.
2. Added native regression `TestP6_NestedJoinSameNameIntermediatePinsGroupOutput` from selectD 2.4/2.5; it fails with `[222 x2 555 x5 555 x5]` vs `[222 x2 444 x4 555 x5]`. Existing native test pins final unaliased and aliased forms.
3. SQLite `select.c` treats parenthesized joins as FROM-subquery/co-routine outputs: emitted values are positional, so duplicate column names stay distinct. Vector propagation design: store built `allRows[i]` at `positionalRowKey` in `execSelectJoins`; pass visible left/right defs to `buildCombinedRowMap`; concatenate left vector (or derive left base values) and right vector (or derive right base values) for each join outcome, accounting for USING/NATURAL merged columns and NULL-padded LEFT/RIGHT rows. Then preserve vector in `projectSubqueryRowMaps`. Boundary assignment alone was tried and failed; reverted.
4. Implemented positional propagation: materialized subquery maps retain exact result row vectors; join-group operands move their vector to a separate right-side private key; each applyJoin composes left/right visible vectors into the combined map, and star expansion consumes the vector. Duplicate-name tests now pass.
