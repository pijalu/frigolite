## 0. Binding roots (these govern every item below)

1. **All tests pass.** The end state of this plan is a green suite: every
   `TestSQLiteSuite` leaf and every native test. "Mostly green", "green except
   the WAL families", "documented as a known gap" are *not* end states.
2. **A TCL test may be marked obsolete only when the same functional aspect is
   covered by a native test.** An obsolete marking is a *substitution*, never a
   dismissal: the native test must exercise the same behaviour (same input,
   same observable contract), must live in the repository as a runnable Go
   test, and the obsolete record must name that test. Without the native
   replacement, the TCL test stays and is fixed.
3. **No descoping of functional coverage.** The skip lists
   (`slowTestFiles`, `unsupportedTestFiles`, `harnessSkipSubtests`) do not grow;
   expectations are never weakened to make a test pass; a fixture is never
   trimmed to hide a defect; and no failing leaf is reclassified as "not our
   problem" (GUIDELINES §1d).
4. **Every failure is owned.** Each failing leaf is classified (C1–C5, §3) and
   attached to a work item; the work item's exit criterion is a green test (or
   a native replacement + an obsolete record that satisfies root 2).
5. **Evidence, not assertion.** Every item closes with a run log (or a native
   test run) recorded in §7, and the baseline in §2 moves monotonically down.

### What "marking obsolete" may look like (and what may not)

| allowed | not allowed |
|---|---|
| A TCL test whose behaviour is fully covered by a named native Go test (e.g. the testfixture helper's *Tcl-level* contract is covered by `TestSQLite…`), with the native test named in the obsolete record | dropping a TCL test because the engine "cannot" do it yet |
| A TCL test that duplicates a native test for the same contract | weakening a `do_execsql_test` expectation to match a wrong engine behaviour |
| A TCL test that tests the *testfixture itself* (not SQLite) and has no functional counterpart | adding a family to `unsupportedTestFiles` to silence a red family |
| | replacing a red assertion with a skip inside the harness |

## 1. Definition of parity (exit criteria)

1. `go test -p 1 ./... -count=1` → the root package passes; `TestSQLiteSuite`
   reports **0 failing leaves**.
2. The skip lists (`slowTestFiles`, `unsupportedTestFiles`, `harnessSkipSubtests`)
   are **unchanged** — every entry still needs an implemented feature or a
   documented, evidence-backed exclusion, never a "skip because red".
3. Every family in `ori/sqlite/test` has a fixture in `testdata/` that was
   generated by the *current* converter and verified by the batch procedure
   (§5), i.e. no stale fixture hides a defect.
4. `go run ./tools/status ledger` is green, `tools/status --check` passes, and
   the green ledger records the same families as the harness.
5. For every remaining difference the *root cause* is one of the four classes
   in §3 and is recorded in `.agents/lessons_learned.md` — no "pre-existing"
   or "out of scope" leftovers (GUIDELINES §1d).

## 3. Root-cause taxonomy (every failure belongs to exactly one class)

| class | meaning | where it is fixed | cost profile |
|---|---|---|---|
| **C1 converter** | the TCL→fixture conversion is unfaithful (a missing command, a wrong substitution, an unsupportable runtime loop) | `tools/tclconvert/tcl/` | cheap, multiplies across families |
| **C2 engine** | the engine's behaviour differs from SQLite | `internal/` | medium; oracle-verifiable per case |
| **C3 harness protocol** | the fixture model cannot express the test (a missing step type, a missing Tcl proc) | `frigolite_harness_test.go` | cheap per case |
| **C4 feature gap** | a whole SQLite feature is missing (stmt-status counters, shared cache, multiplex VFS, blob I/O, auxdata, UTF-16) | `internal/` + `frigolite.go` | large; each needs its own goal file |
| **C5 stale fixture** | the installed JSON predates the current converter and hides or invents failures | regenerate + batch | mechanical, but each family needs triage |

**Triage rule (GUIDELINES §1c)**: for every family, write a pure-Go test
against `frigolite.Open/Exec/Query` first. If it fails → C2/C4 (engine). If it
passes while the family fails → C1/C3 (converter/harness). Never guess.

## 5. Execution procedure (binding)

1. **Baseline** — `go test -p 1 ./... -count=1` with a unique log; extract
   the leaf set with
   `grep -a -o "FAIL: TestSQLiteSuite/[^ ]*" <log> | sed 's/ (.*//' | sort -u`.
2. **Triage first** (GUIDELINES §1a/§1c) — a pure-Go test per family, then
   the oracle (`/usr/bin/sqlite3`, `/opt/homebrew/bin/tclsh`).
3. **Plan, then edit** (GUIDELINES §1b) — a work card naming the files, the
   ordered steps and the verification.
4. **Convert** — `mkdir -p /tmp/regenN && go run ./tools/tclconvert/ -outdir
   /tmp/regenN` (the converter does **not** create the outdir).
5. **Batch-verify** — `/tmp/regen3-batch.py` (env-parameterized): install the
   fresh fixture, re-run, revert on a regression. **A build failure is "no
   result", never "0 failures"**; never edit the engine while a batch runs.
6. **Pin** — a native Go pin test per behaviour change (`frigolite_*_pin_test.go`).
7. **Close** — update `handover.md`, `.agents/lessons_learned.md`, this plan's
   inventory table, and the green ledger (`tools/status ledger`).

## 6. Risks

| risk | mitigation |
|---|---|
| A converter change has a wide blast radius | the batch reverts any family with a regression; never batch while the engine is edited |
| Fixture size/memory blow-up | the converter's 150k-statement budget and 30 s deadline stay in force; oversized files stay conversion errors; the full suite peaks at ~7.4 GB RSS and the GC reclaims between families |
| The full suite is slow (~55 min) | run it in the background with a unique log; use `FRIGOLITE_TEST=<family>` for iteration |
| Feature gaps (W4) are large | one goal file each, UCL first, and they are sequenced *after* the converter/engine work, which is cheaper per leaf |
| "Parity" measured against the wrong corpus | the corpus authority is `ori/sqlite/test` (3.54-equivalent), not the pinned `../sqlite` (3.51) |

## 6b. Harness robustness (do this first — it prevents crashes)

A failed database open used to leave the harness's handle nil, so the *next*
test case dereferenced it and the whole suite aborted with a panic (run 12 hit
this in `e_walckpt/setup_4`). Every open site now reports the error and falls
back to an empty database, so a failing family degrades into failing leaves
instead of killing the run. **Any new harness step that opens a database must
follow the same rule.**
