## 1. indexexpr2 — 50 leaves (run-33 41) → THREE root causes, one of them a single line

### 1a. BETWEEN with a NULL bound must not short-circuit to NULL (~40 leaves)

**Leaves**: 8.1.1, 8.1.2, 8.3.{1..12}.2, 8.5.{13..25}.{1,2} — the dominant class.

**Engine site (the bug)**: `internal/execexpr/expression_eval_tail.go:183-185`

```go
if isSQLNull(low) || isSQLNull(high) {
    // SQLite: any NULL bound makes the whole BETWEEN NULL.
    return nil, nil
}
```

That comment is wrong. SQLite does not evaluate BETWEEN as a primitive: the
code generator lowers `x BETWEEN a AND b` to `x>=a AND x<=b` (expr.c,
`sqlite3ExprCodeTarget`, case TK_BETWEEN) and the AND is Kleene: FALSE
dominates NULL. So when the other comparison is provably false, the whole
BETWEEN is FALSE, not NULL.

**Oracle** (setup `CREATE TABLE t0(c0); CREATE INDEX i0 ON t0(c0) WHERE c0 NOT NULL; INSERT INTO t0(c0) VALUES (NULL);`):

```sql
SELECT ~('' BETWEEN t0.c0 AND TRUE) FROM t0;          -- oracle: -1   (ours: NULL)
SELECT ( 0 == (34 BETWEEN c0 AND 33)) IS TRUE FROM t0; -- oracle:  1   (ours: 0)
```

`''>=NULL` is NULL, `''<=1` is FALSE, `NULL AND FALSE = FALSE = 0`, `~0 = -1`.
Fix: delete the short-circuit; evaluate both comparisons and combine through
`kleeneAnd` (`internal/execexpr/expression_compare.go:174` — that helper is
already correct: FALSE-dominant). This also fixes 8.5.13-25
(`10 BETWEEN y AND b` with y NULL under LEFT JOIN t2).

**Native repro** (fixture steps 8.0/8.1.2; harness line numbers in
`/tmp/probe-indexexpr2.log`): see the two SQL statements above.

**Unit card**: "BETWEEN NULL-bound short-circuit" — first action: replace the
short-circuit with two comparisons + `kleeneAnd` (NOT BETWEEN negates after),
pin with the two oracle statements + the 8.3 sweep. **Size S**. Watch: make
sure the row-value BETWEEN path (`evalBetweenRowValue`) keeps its own correct
TFL.

### 1b. `SELECT *` / LEFT-JOIN WHERE with FALSE AND NULL still filtered (8.5.1-12, 8.5.x.1 WHERE variants)

8.5.{1..12}.{1,2}: `SELECT ( 0 == (a=0 AND y=1)) IS TRUE FROM t1 LEFT JOIN t2`

### 1e. Expression-index maintenance counting (2 leaves: 4.120, 4.130)

Fixture: `runtime_var cnt` after `UPDATE t1 SET b=b+1` (want 2) and `UPDATE t1

### 1f. Aggregates in correlated scalar subquery (1 leaf: 11.0)

### 1g. Plan-order divergence (1 leaf: 1.2)

`SELECT 'TWOX' == (b || 'x') COLLATE nocase FROM t1 WHERE (b || 'x')>'onex'` →

**Card summary**: 1a = S (one site), 1b = S-M, 1c = M (vtab), 1d = M

## 3. e_reindex — 96 leaves (run-33 97) → 1 real engine gap + one harness isolation artifact + cascade

The run-33 card's third class (FTS shadow `ta_segdir`, ~19) does **not appear**
in this tree — zero `segdir` mentions in the family log. Class list now:

### 3a. integrity_check does not verify index/table entry consistency (1.3)

Source e_reindex.test:96-107 (`e_reindex-1.3`): after deleting the index rows
from `sqlite_master` (writable_schema), mutating the table, and re-inserting
the index entries, `PRAGMA integrity_check` must report exactly:

```
wrong # of entries in index i2
wrong # of entries in index i1
row 3 missing from index i2
row 3 missing from index i1
row 4 missing from index i2
row 4 missing from index i1
```

**Engine**: `internal/execpragma/execpragma.go:371` maps INTEGRITY_CHECK →
`st.QuickCheck` → `internal/exec/pragma_quickcheck.go` (`execQuickCheck`),
which verifies NOT NULL / STRICT / CHECK / UNIQUE **by grouping table rows**
(its own comment: "The engine does not maintain secondary index btrees [for
this check], so index uniqueness is verified by grouping the table rows by
index key"). It never opens the index b-trees, so it can never produce
"wrong # of entries in index X" / "row N missing from index X" — the corruption
setup (which our engine runs fine) yields `ok`.

Classification: **engine gap**. SQLite's pragma.c `integrityCheck` walks each
index with `checkTreePage`, compares entry counts against the table, and
verifies per-row presence. Unit: add the index-walk pass to
execQuickCheck (count + per-row presence, ordered diagnostics), gated on the
same N-limit argument. **Size M-L** (needs index b-tree walk infra; quick_check
semantics must stay: quick_check skips the per-row presence pass).

### 3b. ATTACH 'test.db2' shared-filename race → cascade (2.0 … 2.6.8, ~95 leaves)

`e_reindex-2.0` fails with the harness's own annotation: "ATTACH 'test.db2'
hits the file another parallel JSON file keeps attached (shared-filename race);
the REINDEX-subset contracts … are pinned by TestPinReindexRebuildsUnderChangedCollation
and TestPinReindexSecondConnectionMissingCollation" (harness:3145). Every 2.x
leaf downstream then fails with `no such table: t1/t2/aux.t1/collA` (~52) or
`unable to identify the object to be reindexed` (2.4.x/2.5.x REINDEX probes,
~8 — the source e_reindex.test:201-235 runs REINDEX against the aux schema
that never materialized).

Classification: **harness gap** (attachment isolation for named db files
across parallel shards), already flagged and pinned natively. Unit: fixture
isolation (rename the attached file per family or serialize this family), not
an engine change. **Size S** (harness) — the engine contracts are already
pinned.
